## Главные выводы

1. **`switch/case` читается лучше, чем длинная цепочка `if/else if`**, когда мы сравниваем одну переменную с конкретными значениями. Это делает код компактнее и нагляднее.

2. **`int.TryParse()` безопаснее `int.Parse()`**, потому что не выбрасывает исключение при неверном вводе, а возвращает `false`. Это критично при работе с пользовательским вводом.

3. **Логические операторы `&&` и `||` позволяют объединять условия**, делая код более гибким. Например, можно принять и `"A"`, и `"a"` как один и тот же выбор.

4. **Тернарный оператор удобен для коротких проверок**, но вложенные тернарники ухудшают читаемость — лучше использовать `if/else`.

## Ответы на вопросы

### 1. Чем `int.TryParse()` безопаснее `int.Parse()`? В каких случаях стоит использовать каждый?

`int.Parse()` выбрасывает исключение `FormatException`, если строка не является числом, и `OverflowException`, если число слишком большое. Это может «уронить» программу, если не обернуть вызов в `try/catch`.

`int.TryParse()` возвращает `bool` — `true`, если преобразование успешно, и `false`, если нет. Само число записывается в выходной параметр через `out`.

**Когда использовать:**
- `int.TryParse()` — при работе с вводом от пользователя, из файла или сети, где данные могут быть некорректными.
- `int.Parse()` — когда мы уверены в корректности строки (например, значение пришло из проверенного источника).

---

### 2. Когда `switch` удобнее, чем цепочка `if/else if`? Приведите пример из реальной жизни.

`switch` удобнее, когда одна переменная сравнивается с **набором конкретных значений** (констант), и логика для каждого варианта проста. Он делает код компактнее и легче читается, а компилятор может оптимизировать его быстрее.

**Пример из реальной жизни:** обработка команд меню в банкомате.

```csharp
switch (command)
{
    case 1: ShowBalance(); break;
    case 2: Withdraw(); break;
    case 3: Deposit(); break;
    case 4: Exit(); break;
    default: Console.WriteLine("Неверная команда"); break;
}
```

Если бы то же самое писали через `if/else if`, код был бы длиннее и повторял бы сравнение с `command` в каждом блоке.

### 3. Что произойдёт в `switch`, если убрать `break` после одного из `case`?

Произойдёт **«провал» (fall-through)**: выполнение перейдёт к следующему `case` без остановки. В C# это запрещено для непустых блоков — компилятор выдаст ошибку:

> *Control cannot fall through from one case label to another.*

Исключение — если `case` пустой (не содержит кода) или заканчивается `return`, `throw`, `goto` или `break`. То есть «проваливаться» можно только на пустые метки, чтобы объединять несколько значений:

```csharp
case 1:
case 2:
    Console.WriteLine("Один или два");
    break;
```

### 4. Чем отличается `=` от `==` в C#? Почему это частая ошибка?

- `=` — **оператор присваивания**. Записывает значение в переменную: `x = 5;`
- `==` — **оператор сравнения**. Проверяет равенство и возвращает `bool`: `if (x == 5)`

Это частая ошибка, потому что:
1. Синтаксически они похожи — легко пропустить один символ.
2. В некоторых языках (например, в C) `if (x = 5)` — валидная конструкция (присваивание с ненулевым результатом трактуется как `true`), что порождает трудноуловимые баги.

В C# эта ошибка отловится компилятором: `if (x = 5)` вызовет ошибку, потому что результатом присваивания является `int`, а не `bool`. Но в выражениях, где тип совпадает, ошибка всё равно может проскочить.

### 5. Можно ли написать тернарный оператор внутри другого тернарного оператора? Приведите пример из кода лабораторной и оцените читаемость такого кода.

Да, можно. Тернарный оператор — это выражение, и оно может быть вложено в другое выражение.

**Пример из лабораторной:**

```csharp
string result = answer == "груша"
    ? "Дракон пропускает вас"
    : attempts < 2
        ? "Неверно! Попробуйте ещё раз."
        : "Дракон вас съел!";
```

**Оценка читаемости:** вложенные тернарные операторы удобны, когда ветвей всего 2–3 и они короткие. Но если вложений больше двух, код становится трудночитаемым: сложно понять порядок вычислений и приоритет условий. В таких случаях лучше использовать `if/else if/else` — он нагляднее и проще для сопровождения.
